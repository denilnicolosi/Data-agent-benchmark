# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A LangGraph workflow, served via **Aegra** (self-hosted Agent Protocol server), that fans out an analytical request into 4 independent parallel pipelines: Pandas, Dask, NumPy, Polars. Each branch generates code (LLM), pauses for human approval via `interrupt()`, then runs the approved code inside its own isolated Docker container to collect timing/memory metrics. Branches merge, a final interrupt lets the user pick the winning strategy, and a Markdown report + chart get generated.

The agent code lives in `src/benchmark_agent/` (matching Aegra's expected project structure). LLM and Docker nodes are **async**; LLM nodes use **RetryPolicy**. All 12 per-library branch nodes are generated via factory functions in `nodes.py` to eliminate code duplication.

## Commands

```bash
pip install -r requirements.txt        # install deps (or: uv sync)
cp .env.example .env                   # then set LLM_MODEL + the provider API key, and TELEGRAM_* (required for bot_handler.py)

python data_generator.py               # (optional) pre-seed data/analytics.db with 100k synthetic rows
aegra dev                              # starts the Aegra server (auto-starts Postgres via compose), hot-reload ON.
                                       # REQUIRES UVICORN_RELOAD_EXCLUDES=output/*/*.py in .env (aegra dev loads
                                       # .env; the uvicorn CLI reads UVICORN_* env vars): it excludes the winning
                                       # script the report node writes into output/<thread-id>/ from the reload
                                       # watcher. Only that exact pattern works; "output" or "output/*" do NOT
                                       # (uvicorn's FileFilter matches via Path.match suffix semantics).
# No-reload alternative: Linux/macOS `aegra dev --no-reload`. On Windows that variant BREAKS
# psycopg (without reload uvicorn stays on the ProactorEventLoop); use plain `aegra dev`
# with the exclude pattern above.
python bot_handler.py                  # separate process: waits for /newsession from Telegram, runs the session (HITL approval/selection), then loops back for a new request
```

There is no test suite, linter, or formatter configured in this repo; don't assume `pytest`/`ruff`/`black` exist.

The Docker image used for benchmark execution (`benchmark-runner`, from [Dockerfile.benchmark](Dockerfile.benchmark)) is built automatically on first use by `src/benchmark_agent/docker_runner.py`; no manual `docker build` needed.

## Architecture

### Graph shape ([graph.py](src/benchmark_agent/graph.py))
`START` fans out directly to 4 independent chains (`generate_<lib>` → `approve_<lib>` → `run_<lib>_docker`) → all 4 join at `merge_results` → `generate_report`. The `approve_code` interrupt has **three outcomes** (stored in `<lib>_decision`): `"approve"` runs the code in Docker, `"regenerate"` routes back to `generate_<lib>` (**no limit**; the regeneration prompt includes the previous code so the model produces a different implementation; `<lib>_attempts` counts generations for display only), `"reject"` goes to `run_<lib>_docker` which skips execution and records a failed benchmark ("Rejected by the user."). After `run_<lib>_docker` a second conditional router (`make_execution_router` in nodes.py) implements the **execution-fix loop**: if approved code fails at runtime, it routes back to `generate_<lib>` with the failing code + error in the prompt, up to `MAX_EXECUTION_FIXES` (3) fixes, tracked via `exec_attempts`; the error travels in `exec_error` (cleared on success) and is shown in the next approval message. Failures flagged `infra: True` by the runner (docker daemon down, staging error, broken wrapper output, as opposed to failures OF the generated code) bypass the fix loop entirely: regenerating code can't fix infrastructure. Success, rejection, infra failure, or an exhausted fix budget proceed to `merge_results` (which has `defer=True`, so uneven branch lengths are fine). There is no setup node: only `analytical_request` must arrive in the run input; the generate nodes validate it and raise a fail-fast `ValueError` (deliberately NOT retried by `default_retry_on`) when it's missing or empty. Paths are deliberately NOT in the state; the DB location comes from the `ANALYTICS_DB_PATH` env var (default `data/analytics.db`, resolved in `run_in_docker`) and the DB is generated server-side on first use by `docker_runner._ensure_database()` (serialized with an asyncio lock across the 4 parallel branches). State ([GraphState](src/benchmark_agent/graph.py)) nests one `BranchState` per library under its own top-level key (`pandas`, `dask`, `numpy`, `polars`), each annotated with the `merge_branch` **custom reducer**. The 4-way fan-in into `merge_results` is conflict-free because each branch only ever writes its own key; the reducer exists for the *sequential* partial updates within a branch; without it, LangGraph's default reducer would replace the whole sub-dict on every node update (e.g. `approve_<lib>` writing only `decision` would wipe `code`). Nodes therefore return nested partial updates like `{"pandas": {"decision": "approve"}}`.

LLM generation nodes have a **RetryPolicy** configured (3 retries w/ backoff, passed as `retry_policy=`). The Docker nodes have none: `run_in_docker` never raises (every failure comes back as a metrics dict), so a policy there would never fire. All I/O-bound nodes (generate_*, run_*_docker and generate_report, which makes the commentary LLM call) are **async**.

### Human-in-the-loop protocol - read this before touching `bot_handler.py`
`bot_handler.py` is an **external** process, not part of the graph; it drives Aegra's REST API to find pending interrupts and resume them. This is the most non-obvious part of the codebase:

- There is no fixed-rate polling: the bot blocks on `GET /threads/{tid}/runs/{rid}/join`, which Aegra holds open (heartbeat `\n` every ~5s) until the run reaches a terminal state, and `interrupted` **is** terminal (`TERMINAL_STATES = {"success", "error", "interrupted"}` in aegra_api). After each resume the bot joins the new run_id. Aegra reports failures as status `"error"` (not `"failed"`); the bot accepts both. Webhooks are not implemented by Aegra for runs (the `webhook` field exists only on crons, unwired).

- There is no dedicated `/resume` endpoint. Resuming means creating a **new run** on the same thread: `POST /threads/{thread_id}/runs` with `{"assistant_id": ..., "command": {"resume": <value>}}`. Every resume returns a **new `run_id`** that must be tracked for subsequent polling (the old one stays stuck in `"interrupted"` forever).
- Because all 4 branches can be paused on `interrupt()` at the same time (same thread, same superstep), resuming with a flat value is ambiguous; LangGraph would apply it to whichever pending branch happens to replay first. To approve/resume **one specific branch** without touching the others, the resume value must be a dict keyed by that interrupt's own `id`: `{"command": {"resume": {interrupt_id: value}}}`. `resume_run()` in [bot_handler.py](bot_handler.py) implements this; don't regress it back to a flat value.
- Thread state (`GET /threads/{thread_id}/state`) is thread-scoped and reflects all currently pending interrupts regardless of which `run_id` is "current"; that's what `bot_handler.py` polls to discover new interrupts.
- The bot is built on **python-telegram-bot** (async `Application` + handlers), and all Aegra REST calls use **httpx**; there is no `requests` usage and no manual `getUpdates` offset management. Telegram (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`) is **required**; the old CLI fallback was removed. Handlers are restricted to the configured chat via `filters.Chat`.
- Session lifecycle: `/newsession <request>` (or plain text while idle) triggers `start_session()`, which runs `run_workflow()` as an asyncio task on a **fresh Aegra thread** (so state resets automatically). One session at a time (`SessionState.running`); when it ends (success/failure/exception, or `/cancel` which cancels the asyncio task) the `finally` block resets state and re-sends the "ready" prompt. On success the bot also uploads `performance_chart.png` (photo) + `data_analysis_report.md` + `approved_analytics_solution.py` (documents) into the chat via `send_artifacts()`; best-effort: files not visible from the bot's filesystem (full-container mode) are silently skipped, the final message already lists their paths. A cancelled session just abandons its interrupted Aegra run, safe because every session gets a fresh thread.
- HITL wiring: the workflow task asks questions via `ask_with_buttons()`, which parks an `asyncio.Future` in `SessionState.pending` keyed by `"approve_code:<library>"` or `"select_strategy"`; `on_button` (the `CallbackQueryHandler`) resolves the matching future and acknowledges the press with a callback toast + removal of the inline keyboard (no extra chat message); stale presses (question already answered) get an "Already handled." toast and their leftover keyboard cleared. Telegram caps `callback_data` at 64 bytes; keep button payloads compact: the approval keyboard (✅ Approve / 🔄 Regenerate / ❌ Reject) encodes the choice as `"d": "a"|"g"|"x"`, expanded via the `DECISIONS` map before resuming with `{"decision": "approve"|"regenerate"|"reject"}`. When the interrupt payload carries `execution_error` (code that failed at runtime and was auto-regenerated), the approval message shows the error above the fixed code with the fix counter (`fix_attempt`/`max_fix_attempts`).

### Code generation ([nodes.py](src/benchmark_agent/nodes.py), [prompts.py](src/benchmark_agent/prompts.py), [prompt_store.py](src/benchmark_agent/prompt_store.py))
All 12 per-library branch nodes (`generate_*`, `approve_*`, `run_*_docker`) are created by 3 factory functions (`_make_generate_node`, `_make_approve_node`, `_make_run_docker_node`) rather than being manually duplicated.

Prompts are fetched **per call** through `prompt_store.get_prompt("benchmark/<lib>"|"benchmark/commentary")` (via `asyncio.to_thread`, the SDK client is blocking). With `LANGFUSE_PROMPTS=1` (+ `langfuse` package + the LANGFUSE_* keys) the text comes from **Langfuse Prompt Management** (label `LANGFUSE_PROMPT_LABEL`, default `production`, SDK cache ~60s), and the prompt's `config` may carry `{"model", "max_tokens"}` which override the env vars in `get_llm()`, centralizing prompt AND model. In every other case (flag off, package missing, prompt not seeded, Langfuse down) the authoritative fallbacks in prompts.py are used, so the repo works fully offline. Prompts use Langfuse's native **`{{mustache}}` variables** (recognized by the Playground and UI experiments): `get_prompt(name, variables)` returns the text already compiled, via the SDK's `prompt.compile()` on the Langfuse path, via `compile_local()` (equivalent single-pass regex, inserted values never re-scanned) on the fallback path. Keep the `{{placeholders}}` intact when editing; single literal braces in prompt text or variable values are safe. `seed_langfuse_prompts.py` (repo root) seeds/re-versions the 5 prompts from the local files. Every LLM call carries a `run_name` (`generate_<lib>`, `report_commentary`) and metadata (`library`, `phase` = generate|regenerate|fix|commentary, plus `prompt_name`/`prompt_version` when the text came from Langfuse) so the OTEL spans in Langfuse are identifiable and filterable; this metadata is the only trace↔prompt-version link, since OTEL-side tracing has no automatic one. Each `generate_<lib>_node` calls `generate_code_with_llm` (async), which uses **structured output** (`with_structured_output` on the pydantic model `GeneratedSolution`) to get `reasoning` and `code` as separate fields, no markdown-fence parsing (a fence-stripping safety net remains). Structured output embeds the script in a JSON string field, and some models (NIM-served nemotron, gpt-oss) corrupt the escaping (literal `\"`/`\n`, leaked closing braces), producing code that never compiles: any `CodeGenerationError` from the structured path therefore triggers **one plain-text fallback** (`_generate_plain`: reasoning paragraph + fenced script, parsed by `_parse_unstructured`), and `LLM_STRUCTURED_OUTPUT=0` skips structured output entirely to avoid the wasted call on providers known to be broken; the reasoning is carried in state (`<lib>_reasoning`), included in the `approve_code` interrupt payload, and shown above the code in the Telegram approval message. The model is provider-agnostic: `get_llm(model_spec=None, max_tokens=None)` builds it via LangChain's `init_chat_model`; explicit args (from a Langfuse prompt's config) win, otherwise the `LLM_MODEL` env var in `"provider:model"` format (default `openai:gpt-5-mini`; no explicit temperature is passed because reasoning models reject non-default values); the provider's own API key env var (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, ...) must be set, and the matching `langchain-<provider>` integration package installed. `get_llm()` always passes an explicit `max_tokens` (`LLM_MAX_TOKENS` env var, default 16000) because some integrations default to a tiny completion budget (ChatNVIDIA: 1024) and reasoning models burn it on hidden reasoning tokens, silently truncating the generated code mid-file. Three guards keep truncated/garbage code from ever reaching the reviewer, all raising `CodeGenerationError` (a plain-`Exception` subclass, deliberately NOT `ValueError`: langgraph's `default_retry_on` refuses to retry `ValueError`, so the node's RetryPolicy re-samples instead of failing the run): `_is_truncated()` rejects replies whose `finish_reason`/`stop_reason` is a token-limit stop, and `_validate_code()` requires the final code (from any parsing path) to `compile()` and to define `analyze(`. The analytical request injected from graph state is deliberately the **only** specification of what to compute; don't hardcode a concrete analysis or fixed result keys into the prompt templates (it would conflict with user requests coming from Telegram). The only hard contract is that generated code defines `analyze(db_path: str)` returning a dict of named results; that's all `wrapper.py` requires. The `{{analytical_request}}` variable is compiled by prompt_store (never `str.format()`), so the templates may contain literal single braces. The prompts also declare the benchmark container's library versions (pandas 3.x, polars 1.x, numpy 2.x, dask 2026.x) plus per-library API guardrails; LLMs otherwise generate pre-1.0 Polars (`read_database(connection_uri=...)`) and pandas-2 idioms that crash at runtime; keep these notes in sync with what `Dockerfile.benchmark` actually installs if the image is ever rebuilt.

### Docker execution ([docker_runner.py](src/benchmark_agent/docker_runner.py), [wrapper.py](wrapper.py), [Dockerfile.benchmark](Dockerfile.benchmark))
`run_in_docker()` (async; runs `subprocess.run` in a worker thread via `asyncio.to_thread`; asyncio subprocesses need the Proactor loop on Windows, but the server must stay on the Selector loop for psycopg) has two modes, selected by the `BENCHMARK_SHARED_VOLUME` env var:
- **Host mode** (`aegra dev`, var unset): writes the generated script to `<system-temp>/benchmark_scripts/` (deliberately OUTSIDE the project tree: `aegra dev` hot-reload watches project `*.py` and a script written inside it would restart the server mid-benchmark) and bind-mounts it plus the SQLite DB read-only into a `benchmark-runner` container.
- **Full-container mode** (`docker compose up`, var set by the compose file): the API container talks to the **host** docker daemon via the mounted socket, so bind mounts of container-local paths would come up empty. Instead `_prepare_run()` stages the script and a per-run private DB copy into a shared **named volume** (mounted at `BENCHMARK_SHARED_DIR`, default `/shared`); the sibling benchmark container mounts the volume by name and `wrapper.py` locates the files via `SCRIPT_PATH`/`DB_PATH` env vars (defaults keep host mode working). If the `benchmark-runner` image predates the env-aware wrapper it must be rebuilt manually; `ensure_docker_image_built()` only builds when the image is missing.

Container execution is **serialized** across the 4 branches by a module-level asyncio lock (`_benchmark_lock`): LLM generation and approvals stay parallel, but the actual measurements run one at a time so the containers don't compete for CPU/RAM and skew the numbers. Every benchmark container runs with `--network none` (generated code needs no network; the DB is a local file) and capped resources, `BENCHMARK_MEMORY_LIMIT` (default `2g`) and `BENCHMARK_CPU_LIMIT` (default `2`), so all libraries are measured on identical hardware budgets. Failures are **classified** via the `infra` key in the metrics dict: `infra: True` for infrastructure problems (docker exit code 125, daemon connect errors in stderr, any host-side exception, wrapper output that isn't parseable JSON despite exit 0), `infra` absent/False for failures of the generated code (script errors reported by the wrapper, OOM kills, and the 120s timeout; the timeout is deliberately NOT infra because slow code is exactly what the LLM fix loop can address). Only non-infra failures enter the execution-fix loop.

The wrapper dynamically imports the script, calls `analyze(db_path)`, times it, tracks **peak RSS** via a background thread sampling at 10ms intervals, and prints a JSON line to stdout. The host-side parser searches from the last stdout line backwards for valid JSON, making it robust against user code that prints to stdout.

### Report generation
`generate_report_node` in `src/benchmark_agent/nodes.py` writes all session artifacts (`approved_analytics_solution.py`, `data_analysis_report.md`, `performance_chart.png`) into one per-session folder. The report's "Analysis of Results" section is computed from the **measured metrics** by `_analysis_section` (speed ranking with relative multipliers, lowest-memory branch, per-branch failure reasons, not-executed branches); do not reintroduce canned per-library prose there: it can contradict the actual numbers in the table above it. Below it, `_generate_commentary` adds a "Commentary (LLM)" section: ONE async LLM call (same `get_llm()` model as generation, prompt `REPORT_COMMENTARY_PROMPT` in prompts.py) that receives the full session picture: every branch's status/metrics, result preview, and the exact code that ran, so it can explain WHY the numbers came out that way and flag result discrepancies. It is strictly best-effort: any exception or a token-limit truncation returns `""` and the section is omitted; the report node (now **async**) must never fail or block at the last step of the run. Artifacts go into `<OUTPUT_BASE_DIR>/<thread_id>` (base from the `OUTPUT_BASE_DIR` env var, default `output`; thread id from the run's `config["configurable"]`, with a timestamp fallback for runs without a thread). Nothing path-related travels in state or run input; `bot_handler.py` derives the same folder from its own thread id + the shared `.env`. If you change `OUTPUT_BASE_DIR`, update `UVICORN_RELOAD_EXCLUDES` to `<base>/*/*.py` or `aegra dev` hot-reload will restart mid-run. The chart is referenced from the report with a relative link. As its last step the report node calls `_push_session_score` (best-effort, via `asyncio.to_thread`): with the `LANGFUSE_*` keys set it pushes 3 session-level NUMERIC scores to Langfuse (`code_errors`, `branches_failed`, `human_regenerations`, all deliberately oriented so that **higher is worse**, so a model-vs-model dashboard reads without per-metric inversion; `branches_failed` counts every branch without a successful benchmark, whatever the cause, unlike `code_errors` which excludes rejections and infra failures) keyed by thread id, landing on the same Langfuse session as Aegra's traces; without keys or thread id it's a no-op. Each score also carries the session's model slugged into its Langfuse **`environment`** (`openai:gpt-4o-mini` → `openai-gpt-4o-mini`, matching the SDK's `^(?!langfuse)[a-z0-9_-]+$`), resolved by `_session_environment` from the **branch states**, not from `LLM_MODEL`: a Langfuse prompt config can override the model per library, so the env var is only the fallback for a session where no branch generated; branches disagreeing yields `"mixed"`. That is why `generate_code_with_llm` returns `(code, reasoning, model_spec)` and `BranchState` has a `model` key. Of the score's own dimensions only `name` and `environment` are free-form. The dashboard shape this enables: one widget per metric, filter `name = <score>`, breakdown dimension `environment`. Note Aegra exports traces via OTLP rather than the SDK, so trace/observation widgets stay on `environment=default`.
